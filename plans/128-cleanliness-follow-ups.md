## Why

The post-merge audit of plan 127 (2026-11-21, tree `73606226`) left six
verified findings, all older than plan 127:

1. `packages/usage-store/src/migration.ts` throws plain `Error` (schema newer
   than supported, incompatible local machine projection, quota stream budget).
   `connections.ts` maps every failure of the writer open to `storage-failure`,
   so the reader says `schema-too-new` where the writer says `storage-failure`
   for the same store. `migration-failure` is in the reason vocabulary
   (`errors.ts`) and is branched on in `apps/web/src/lib/server/rpc/sync.ts` and
   `apps/web/src/server/sync-data.server.ts`, but nothing produces it.
2. `migrate()` is one function of about 660 lines.
3. Ten `*StoreDependencies` interfaces repeat the same four functions and
   `index.ts` wires them by hand. Cause: `migration.ts` imports schema SQL from
   the store files and `connections.ts` imports `migration.ts`, so a store that
   imported `connections.ts` would close a cycle. `work-thread-store.ts` is
   3,547 lines.
4. Tests read tracked source files and match their text, which `AGENTS.md`
   forbids since #104.
5. `isRecord` is defined 37 times in non-test code: 33 copies reject arrays, 4
   accept them.
6. `apps/web/src/lib/features/work` holds 89 files at one level.

## Design decisions

1. **A1 mirrors the reader.** A store newer than supported fails the writer
   open with `schema-too-new`. Any other failure raised from inside `migrate()`
   carries `migration-failure`. Failures of the open that do not come from
   `migrate()` keep `storage-failure`. Every consumer that branches on the
   reason is traced and the visible change is listed in the execution note.
2. **No schema change anywhere.** `USAGE_STORE_SCHEMA_VERSION` stays 5 and the
   SQL `migrate()` executes, and its order, do not change. A2 is proven by a
   characterization test written first: for a fresh store and every legacy
   shape `migration.test.ts` already builds, the resulting `sqlite_schema`
   rows, `user_version` and migrated data are identical before and after.
3. **A3 breaks the cycle at its cause.** Schema SQL, table lists and
   per-family migrate helpers move to schema modules that import no store.
   Stores then import `connections.ts` and `errors.ts` directly and export
   plain functions. If a cycle survives that move, fall back to one shared
   dependency interface in one module and say so; do not keep ten.
4. **A4 is move-only**, verified the way plan 127 P2 was: the multiset of
   top-level statements is the same before and after.
5. **Source-text tests (A5, B2, C1).** In scope: a test that reads a tracked
   source file of this repository and asserts on its text. Out of scope: a test
   that reads a file it wrote itself, a fixture, a build output or a generated
   manifest. For each in-scope assertion, in this order of preference:
   (a) an existing behavioural or browser test already covers it: delete the
   assertion and name the covering test; (b) rewrite it through a model, store,
   HTTP or browser seam; (c) it guards an import or layering rule: express it
   in the existing checker (`tools/check-package-boundaries.ts`) or a Biome
   restriction, not in a text match; (d) none of these is possible without
   changing production code beyond a small seam: leave it and list it with the
   reason. Coverage of a behaviour is never dropped silently.
6. **D1 adds no package and no dependency edge.** Inside a package, one
   definition and imports of it. Across packages, reuse an export only where
   the `package.json` dependency already exists and the browser bundle guard
   stays green. The four array-accepting copies are unified only where the call
   sites prove arrays cannot change the outcome; otherwise they keep their
   behaviour under a name that says so.
7. **B1 is a move.** `git mv` into subfolders by concern, import paths and path
   strings updated, nothing else. Dead modules are deleted only after a
   repo-wide search finds no importer.

### Findings for the operator (pre-existing, not fixed here)

Both are in migration code, which this plan may not change. Each is pinned by
a named test in `migration-outcomes.test.ts` that fails when a fix lands.

1. **`work_fact_run_state.outcome_code` loses its CHECK on migrated stores.**
   `migrateWorkFactSchema` adds the column with `ALTER TABLE … ADD COLUMN`,
   which cannot carry the constraint a fresh store declares. A store created
   between #67 (`4088634a`, 2026-10-25) and #74 (`fbb8c50b`, 2026-10-26) has
   the column without it. Reproduced on disposable stores; inferred, not
   observed, for real ones. Impact today is low: `recordWorkFactRun` validates
   the value and `queryWorkFactRunStates` skips and counts an invalid row. It
   is the only one of the 28 additively added columns that diverges from the
   fresh DDL. A fix is a table rebuild migration.
2. **The skill collection backfill reads a column a later step adds.**
   `backfillSkillObservationCollectionState` (step 7) selects
   `usage_rows.source_authority`, added by `addUsageRowColumns` (step 15). A
   store last opened by a build older than `85b7c2a7` (2026-07-15) fails the
   writer open with `migration-failure` ("no such column: source_authority");
   the transaction rolls back and the store is untouched. Reproduced on a
   disposable store. A store in continuous use is not affected; an old backup
   would be. A fix moves the backfill after `addUsageRowColumns`.
